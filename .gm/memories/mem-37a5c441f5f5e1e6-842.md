gm-method: when a user asks to reconcile a sibling/consumer repo's content into an SDK/library repo ('take missing content from ../other-repo'), the correct triage is per-file: distinguish generic reusable MECHANISM code (framework-agnostic-ish glue with zero product-specific branding/copy/data baked in — the migration candidate) from product-specific CONTENT/domain logic (page compositions, catalog data, product-specific business logic tied to that product's own endpoints/assets — stays in the consumer repo). A single file that hand-rolls infrastructure the SDK lacks (e.g. a bespoke router, a bespoke state manager) is the clear signal: port it as a new SDK primitive, generalize away any product-specific naming, and document the migration path for other consumers who may have independently duplicated the same gap-filling code.
