An unreachable lint gate does not sit still -- it rots, and the rot is measurable. Swept 13 repos in the 247420 ecosystem for gates invoked by one entry point only. EVERY gate found unreachable had also gone RED while nobody ran it: freddie lint-swallow-comments 64 violations against a frozen baseline of 40, freddie validate-prd broken outright on a js-yaml default-export change, freddie lint.mjs red on its own HEAD-subject check, thebird lint-i18n-ratchet 13 against baseline 12. So the question at wiring time is never just 'is this gate reachable' but 'does it still pass', and the answer is usually no. Corollary that decides which ones you may actually wire: only a gate that is GREEN right now can be wired, because wiring a red gate turns every CI run red and is a different act from closing a reporting hole. Second corollary, subtler: thebird lint-swallow-comments was GREEN yet worthless -- it printed 'scanned 0 files ... PASS: 0 <= baseline 11' because the shared script defaults SCAN_DIRS to src and thebird has only docs/, so green-over-zero-ground is its own failure mode. Third: never wire a gate that self-skips when its dependency is absent (gmsniff lint-undefined-renders skips every route with no server and passes vacuously) -- that ADDS a silently-green gate instead of removing one. The one wireable case, gmsniff lint-gui-ds.mjs, was wireable precisely because it was green AND its sibling-repo-dependent half self-disabled cleanly while its own 9 rule classes still ran.
